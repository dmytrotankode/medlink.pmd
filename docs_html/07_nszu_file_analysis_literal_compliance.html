Потоковий імпорт та 5-кроковий аналіз розшифровки НСЗУ

Процесор OpenXML SAX • Пакетна обробка файлів до 50 000 рядків • Генерація _analyzed.xlsx
Процес імпорту
ЧОМУ ЦЕ РОБИТЬСЯ: У вихідних звітах НСЗУ (як-от Вересень 26.xlsx) повністю відсутні колонки тарифів та оплат. Лікарня отримує лише перелік наданих послуг без розуміння фактичних фінансових надходжень. Модуль повинен самостійно виконати тарифікацію та сформувати доповнений файл.

// C# SAX Streaming: using (var reader = OpenXmlReader.Create(worksheetPart)) { while (reader.Read()) { if (reader.ElementType == typeof(Row)) ParseAndCalculateRow(reader); } }

Аудит 45 колонок та тарифікація за Постановою №1808

Базова ставка 8 735 ₴ • Вагові коефіцієнти ДСГ Wg • Частка 0.55 • Плановість 0.8 • Гірський 1.25
Математичний движок
ЧОМУ ЦЕ РОБИТЬСЯ: Економісту та начмеду необхідно бачити точну формулу розрахунку: чому саме такий тариф нараховано, яка частка глобальної ставки (0.55 для хірургії, 0.60 для терапії), чи враховано плановий коефіцієнт (0.8) або гірський (1.25), та чи виконано умови граничних ліжко-днів.
ЩО РОБИТЬСЯ ПІД КАПОТОМ: Сервіс PmgTariffCalculatorService розраховує: $\text{Tariff} = \text{BaseRate} \times W_g \times K_{\text{share}} \times K_{\text{plan}} \times K_{\text{mountain}}$. Одночасно генерується дерево кроків розрахунку calculation.steps у форматі JSONB для можливості перегляду формули у модальному вікні.
-- SQL розрахунок тарифу стаціонару: SELECT e.id, (8735.0000 * w.weight_coef * s.global_rate_share * CASE WHEN e.is_planned THEN 0.80 ELSE 1.00 END * CASE WHEN org.is_mountain THEN 1.25 ELSE 1.00 END) AS calculated_tariff FROM mis_encounter e JOIN dsg_group_weight w ON w.caption = e.dsg_code;
ЗВІДКИ БЕРУТЬСЯ ДАНІ: Колонка 4 (ID ЕМЗ), Колонка 5 (ДСГ/клас), Колонка 15 (Основний діагноз МКХ-10), Колонка 22 (АКПІ операція). Таблиці: dsg_group_weight (довідник 04_seed_dsg_catalog_465.sql), dsg_tariff_setting.
3

Двостороння 2-Way звірка МІС ↔ НСЗУ (Виявлення невидимих втрат)

Співставлення за encounter_ehealth_id • Виявлення незарахованих випадків та розбіжностей сум
2-Way Звірка
ЧОМУ ЦЕ РОБИТЬСЯ: Частина випадків, внесених лікарями в МІС, взагалі не потрапляє у виплату НСЗУ (відхилені або не враховані до статистики). Без 2-Way звірки лікарня не знає про так звану «невидиму дефектуру» і втрачає мільйони гривень.
ЩО РОБИТЬСЯ ПІД КАПОТОМ: Двосторонній запит з'єднує рядки звіту НСЗУ з медичними картами в МІС. Якщо випадок є в МІС, але НСЗУ виставила статус «Ні» ($0$ грн) або випадок не знайдено — система класифікує його як NOT_FOUND_IN_STATEMENT або REJECTED_BY_NSZU та підраховує точну суму втраченого доходу.
-- 2-Way Matching: SELECT l.encounter_ehealth_id, l.nszu_amount, ar.tariff, (ar.tariff - l.nszu_amount) AS lost_revenue FROM dsg_nszu_statement_line l LEFT JOIN mis_encounter e ON e.ehealth_id = l.encounter_ehealth_id LEFT JOIN dsg_analysis_result ar ON ar.encounter_id = e.id WHERE l.nszu_amount = 0 AND ar.tariff > 0;
ЗВІДКИ БЕРУТЬСЯ ДАНІ: Колонка 4 звіту (ID ЕМЗ) ↔ поле mis_encounter.ehealth_id у тестовій базі evomis-test (перевірено на 17 168 записах). Файл запитів: 02_queries_2way_matching.sql.

Дефектура

Аркуш «Звіт»
ЧОМУ ЦЕ РОБИТЬСЯ: Керівнику закладу та начмеду потрібна зведена фінансова картина: хто з лікарів приніс найбільший дохід, у кого найвищий відсоток браку, та як застосовано правило НСЗУ: для класу «Ургентні стани» у Пакеті 9 оплачується лише 1 послуга на пацієнта в місяць, але в аналізі відображається тариф для всіх лікарів задля оцінки навантаження.
